# Project Specifications: Immortal+

## 1. Project Overview
**Name:** Immortal+
**Description:** A comprehensive, locally hosted Dota 2 coaching application designed to help players improve their gameplay through data-driven insights. It provides live draft suggestions, post-game analysis, mistake identification, and progress tracking over time.
**Safety Priority:** 100% compliant with Valve's anti-cheat policies. The app acts purely as an external observer via public APIs and Game State Integration (GSI) and never hooks into the game memory process.

## 2. Core Features
- **Live Draft Helper**: Uses Dota 2 GSI to read visible draft picks and suggests hero counter-picks and synergies based on current meta win rates, matchups, and the player's personal hero pool comfort.
- **Match History & Analytics**: Deep analysis of past games comparing player performance (Laning, Farming, Fighting, Vision, Objectives) against rank-specific benchmarks (e.g., "What does a Divine player's CS look like at 10 minutes?").
- **Actionable Coaching Items**: Post-game generation of specific things to practice (e.g., "Practice last hitting on Anti-Mage — aim for 50 CS by 10:00 (you had 35)").
- **Progress Tracking**: Daily/weekly snapshots and rolling trend graphs of key metrics (KDA, GPM, Winrate) to visualize improvement over time.
- **Custom 2D Replay Viewer (Planned)**: Local parsing of `.dem` replay files to visualize hero movements, ward placements, and teamfights on a 2D HTML5 Canvas minimap.

## 3. Technology Stack
- **Frontend**: React 19, TypeScript, Vite, React Router 7, Framer Motion (page-transition animations), Recharts (charts), `react-grid-layout` (the editable widget dashboard, via its `/legacy` v1-compatible API), `dotaconstants` (real per-hero base stats / XP tables), `lucide-react` (icons), Vanilla CSS (custom design system, no utility framework).
- **Backend**: Python 3.12, FastAPI, SQLModel (SQLAlchemy + Pydantic), served by Uvicorn. Home-grown SQLite migrations in `database.py` (diffs each model's columns against the live schema and runs `ALTER TABLE`, no Alembic).
- **Database**: SQLite (WAL mode, foreign keys, and a 30s busy timeout all enabled explicitly on connect).
- **External APIs**: OpenDota REST API (primary), Stratz GraphQL API (rank-specific meta, synergy, and a fallback data source), Steam Web API (match history / details / player summaries, and the cluster+replay_salt resolution every parse path depends on), Dota2ProTracker (scraped via Playwright browser automation — no public API, and it's behind Cloudflare bot detection that blocks plain HTTP clients).
- **Replay Parser**: a real, actively deployed Java service (`parser/`) — a vendored fork of `odota/parser` (the same Clarity-based parser OpenDota itself runs), patched to emit real per-second HP/Mana (`Entry.java`/`Parse.java`, four extra fields read straight off the hero entity, same mechanism the existing `life_state` field already used). Built via Maven (`com.opendota:stats`, shaded/uber-jar, not Spring Boot) and published as `ghcr.io/hu1k1e/immortalplus-parser`. **This superseded the original "Placeholder Phase" plan entirely** — it's load-bearing production infrastructure, not a stub.
- **Game Coordinator resolver**: a second Node.js service (`gc-bot/`) not in the original architecture plan — stays logged into a dedicated Steam account via a persistent GC session (`dota2-gc`) to resolve `cluster`/`replay_salt` for arbitrary match IDs Valve hasn't otherwise indexed. Empirically validated live: 25/25 previously-unresolvable matches succeeded through it, vs. OpenDota resolving only ~1/40 and Stratz 0/10 on the same sample (see `research/README.md`).
- **Live draft screen reader**: a separate, non-Dockerized Windows companion app (`draft-scanner/`, Python packaged as a standalone .exe via PyInstaller) that reads picks/bans off the live Dota 2 client via screen capture (ORB feature matching for hero portraits, Tesseract OCR for the ban text log) — the only channel left for non-Captain's-Mode drafts since Valve blanks that data from GSI and (per the 7.35d patch notes) even from Overwolf's sanctioned integration API. Screen-pixels only, confirmed via source read to never touch the Dota 2 process/memory — the same safety category as OBS or Discord's screen share.
- **Deployment**: Docker Compose, 4 services (backend, frontend, replay_parser, gc_bot — see below), images built and pushed to GHCR by `.github/workflows/docker-build.yml` on every push to `main`/`master` (4 parallel jobs, no test/lint gate before publish).

## 4. Architecture
The production stack runs via Docker Compose as **4 services** (`docker-compose.yml`):
1. **`backend`** (`ghcr.io/hu1k1e/immortalplus-backend`) — Uvicorn running FastAPI. Handles all API integrations, caching, business logic, and SQLite database interaction (volumes: `/app/data`, `/app/replays`). Exposed on host ports **9486** (the app's REST API) and **9487** (GSI) — both map to the *same* container port 8000, since GSI payloads land on the same FastAPI app (`POST /api/gsi`) as everything else; the second host port just gives GSI its own firewall/routing story. `REPLAY_PARSER_URL=http://replay_parser:5600` wires it to service 3 below.
2. **`frontend`** (`ghcr.io/hu1k1e/immortalplus-frontend`) — Nginx serving the built React SPA, host port **9485**, proxying `/api` to `backend`.
3. **`replay_parser`** (`ghcr.io/hu1k1e/immortalplus-parser`) — the patched Java/Clarity fork described above, host port **5600**. The backend's `services/local_parser.py` calls its `/blob?replay_url=...` endpoint (downloads + parses + returns one aggregated JSON blob); `services/position_parser.py` calls its root `/` endpoint instead for raw per-second position streams (`/blob` mode drops position data).
4. **`gc_bot`** (`ghcr.io/hu1k1e/immortalplus-gc-bot`) — the Steam GC resolver above, host port **3500**, named volume `immortalplus_gcbot_data` (persists a Steam refresh token so restarts skip re-authenticating), reads `STEAM_BOT_USERNAME`/`STEAM_BOT_PASSWORD` from the stack's environment (a dedicated Steam account, never the user's own — set in Portainer, never committed). First boot needs a one-time Steam Guard code submitted via `POST /steamguard {"code": "XXXXX"}`.

Two more subprojects exist alongside this stack but are **not** part of it (see the new Subprojects & Tooling section below for full detail): `draft-scanner/` (a standalone Windows .exe the end user runs on their own gaming PC, talks to the backend over plain HTTPS) and `research/` (an explicitly separate, not-yet-productionized recommendation-engine prototyping effort, kept out of Docker/CI on purpose).

## 5. Database Schema (SQLite via SQLModel)
- `players`: steam_id (unique), account_id, persona_name, avatar_url, rank_tier, mmr_estimate, plus resumable full-history-backfill state (`history_backfilled_at`/`history_backfill_page`).
- `matches`: Extensively detailed match data (KDA, GPM, XPM, damage, duration, result, position/lane_role, items/backpack/neutral_item, auto-parse retry tracking, and many JSON-string timeline/log fields — gold_t/xp_t/lh_t/dn_t, benchmarks, purchase_log, kills_log, obs_log/sen_log, teamfights, objectives, all_players, chat, draft_timings, opendota_raw).
- `match_analysis`: Computed scores (0-100) for Laning, Farming, Fighting, Vision, Objectives, Death, and generated JSON action items/mistakes/rank comparisons/AI coaching.
- `progress_snapshots`: Daily/weekly aggregations of player performance.
- `hero_meta`: Rank-bracket specific win rates and pick rates synced from OpenDota.
- `hero_matchups`: Hero vs Hero advantage percentages.
- `pro_meta`: Hero/player-name/build fields for a planned "pro player builds" feature. **Dead** — nothing in the codebase populates or reads it; only touched by `database.py`'s migration bookkeeping.
- `action_items`: Specific goals assigned to the player (with completion status).
- `user_settings`: The single-row app config table — every API key (Steam/OpenDota/Stratz/OpenAI), LLM settings, sync/analysis/draft-helper/ProTracker/appearance toggles. This is the real config store per the "no `.env` files for app config" rule; don't confuse it with the empty, unrelated `settings.json` file sitting at the repo root (see the new Subprojects & Tooling section).
- `hero_synergy`: hero_id + ally_hero_id pair stats (matches, synergy score, winrate_together) — real Stratz-only ally-pair data, distinct from `hero_matchups`' enemy-pair data.
- `hero_position_meta`: hero_id + position(1-5) win/pick rates and D2PT rating from ProTracker's `/api/heroes/list` — the primary, reliable meta data source the draft engine and Meta page actually read.
- `hero_position_detail`: a richer per-hero/position breakdown (contest rate, lane advantage %, Radiant/Dire and phase splits, build stats) from ProTracker's `/api/heroes/stats`. **Dormant** — the sync function exists (`protracker.py`) but is deliberately not called from the background loop or manual refresh anymore, after repeated unexplained scraping failures (suspected Cloudflare bot-mitigation flagging the server IP). Kept for a possible future retry.
- `hero_overview`: on-demand per-hero/position "hero detail page" data (builds, ability order, weekly win/pick-rate trend) from ProTracker's `/hero/{Name}` page, cached with a 12h TTL.
- `parsed_replays`: status/JSON-log columns for local replay parsing. **Dead** — no router or service reads/writes it (the `Match` row's own JSON columns hold this data instead); only touched by migration bookkeeping.

## 6. UI / UX Design Philosophy
- **Aesthetic**: Dota 2 client-inspired. Deep dark theme (base `#0a0c10`), glassmorphism overlays, and gold (`#e2b742`), radiant green, and dire red accents.
- **No Utility Frameworks**: Uses purely custom Vanilla CSS with CSS variables to maintain strict control over the visual identity. 
- **Animations**: Staggered fade-ins, soft pulsing on loading states, interactive card hover effects.
- **Configurability**: Every toggle, API key, and threshold lives entirely within the app's Settings UI page, not in environment variables or docker-compose files.

- **2026-09-29 (Widget Dashboard: crash fix + hero-model spotlight redesign)**: User reported the dashboard from the prior session had a real breaking bug (clicking Add Widget, or clicking a widget while editing, went to a blank page) plus several feature requests. Root-caused the crash: `WidgetGrid.tsx` had two independent mechanisms both writing `layout` state for a newly-added widget instance -- a reactive `useEffect` keyed on `widgets` (`ensureLayoutForWidgets`) and the `onLayoutChange` callback react-grid-layout calls on its own compaction pass -- computing different positions for the same new item and fighting each other; since react-grid-layout re-fires `onLayoutChange` on essentially every render once the `layout` prop's reference changes, and the old handler always produced a brand-new array with no equality check, this became a genuine infinite render loop ("Maximum update depth exceeded"), which in a production build silently blanks the page instead of showing React's dev-mode overlay. Fixed by making `addWidget` the single writer (updates `widgets` and `layout` together in one handler, not a reactive effect), memoizing the computed `rglLayout` array, and adding a value-equality bail-out (`layoutsEqual`) in `onLayoutChange` so a no-op update returns the same object reference and React skips the re-render. - `buildings.ts`: Real building screen-position data (patch 7.33, ported from OpenDota's `buildingData733.ts`) with a pixel-scan-calibrated remap into this app's map assets. `getStandingBuildings(matchData, currentTime?)` is the core function several map components share.
- `dota.ts`: Loads `constants/heroes.json`/`items.json`/`abilities.json`. CDN URL builders: `getHeroImage` (wide splash crop), `getHeroIcon` (small square), `getHeroRenderImage` (the transparent 3D model render used by the spotlight widgets -- Valve doesn't expose this path via any generated constants, so it's built from the hero's internal name; callers set an `onError` fallback chain to `getHeroImage` then `getHeroIcon`), `getItemImage`, `getAbilityImage`.
- `heroLevel.ts`: `levelFromXp()` -- derives live hero level from cumulative XP via `dotaconstants`' real `xp_level` table.
- `heroVitals.ts`: `getHeroVitals()` -- real max HP/Mana from documented Dota formulas (`base_health + STR*22`, `base_mana + INT*12`). No real moment-to-moment curve (no timestamped data at this layer) -- full-while-alive/empty-while-dead, flagged `approximate: true`; the fallback when `vitals_t` isn't available.
- `heroes.ts`: A second, simpler static hero table (`HEROES: Record<number, {id,name,img_name}>`) alongside `dota.ts`'s constants-file-backed one -- both used somewhat interchangeably across the app (DraftHelper uses this one; most match-detail components use `dota.ts`'s). Minor duplication, not currently broken.
- `itemId.ts`: `resolveItemIdName()` -- the canonical numeric-item-id to name reverse lookup, built once from `dota.ts`'s `ITEMS`. `MatchTabs.tsx`, `PlayerDetail.tsx`, and `PerformancesExpandedUI.tsx` each also build a near-identical local copy rather than importing this -- same minor duplication pattern as `heroes.ts`.
- `items.ts`: A second static numeric-id to name-key map, separately maintained from `itemId.ts`; only `Matches.tsx` imports this one.
- `matchMeta.ts`: Label getters for OpenDota's numeric `game_mode`/`lobby_type`/region codes.
- `performanceIndicator.ts`: `computePerformanceScore()` -- documented client-side heuristic approximating Stratz's proprietary Performance Score (KDA/GPM/XPM/net-worth blended into a percentile among the 10 players, rescaled to roughly +/-50). Used by `MatchupCard` and the `spotlight-last-match` dashboard widget.
- `rank.ts`: `getRankBadge`/`getRankLabel` from OpenDota's `rank_tier` scale -- medal images from a separate CDN host from `dota.ts`'s.
- `roles.ts`: `getPlayerPosition`/`estimateTeamPositions` -- real 1-5 position when `position_est` is present, else a documented net-worth-ranking heuristic fallback.
- `talents.ts`: Resolves a player's raw `ability_upgrades_arr` into a talent tree / skill-build label / ability take-order. No per-pick timestamp exists for talents (unlike items), so they can't be scrub-animated -- documented limitation, not a bug.
- `heroes_raw.json`, `items_raw.json`, `constants/*.json`: vendored/generated Dota game-data dumps consumed by the lib files above, refreshed via `services/fetch_constants.py` (backend) writing into `constants/`.

### Backend (`backend/`)

- `main.py`: FastAPI entry point. `lifespan` calls `init_db()`+`auto_migrate()` then spawns 5 background `asyncio` tasks (all cancelled on shutdown): `background_sync_loop` (new-match sync, daily snapshot, hero_meta/matchups/synergy every cycle, ProTracker on its own longer interval), `steam_match_poll_loop` (sub-minute-latency Steam fast path), `run_history_backfill_once`, `refresh_player_identity_once`, and `auto_parse_worker`. CORS allows `FRONTEND_URL` plus hardcoded localhost origins. **Router registration order**: `player, matches, settings, meta, draft, progress, gsi`. One inline endpoint: `GET /api/health`.
- `config.py`: Environment-level config only (by design -- everything user-facing lives in the `user_settings` DB row instead, per the no-`.env` rule). `DATA_DIR`/`REPLAYS_DIR`/`DATABASE_URL`, `BACKEND_PORT` (8000), `GSI_PORT` (9487), hardcoded external API base URLs, default rate-limit/cache-TTL constants.
- `database.py`: SQLite engine (`StaticPool`, WAL + foreign keys + 30s busy_timeout). `auto_migrate()` diffs each model's columns against the live schema and runs `ALTER TABLE ADD COLUMN` for anything missing (no Alembic, no down-migrations). Also runs a one-time idempotent fixup normalizing `matches.game_mode`/`lobby_type` rows that were stored as Stratz's raw enum-name strings instead of Valve's integer codes -- documented as having corrupted roughly half of a 5,289-match real history before the fix.
- `models.py`: All SQLModel tables -- see Section 5 for the full, current list (14 tables, including which ones are dead/dormant).
- `test_stratz.py`: **Not a real test** despite the name (no pytest, no assertions) -- an ad-hoc debug script that also references a stale DB filename (`data/immortal.db`, not the real `immortalplus.db`), suggesting it's unmaintained.

## 11. Subprojects & Tooling

Several subprojects live alongside `frontend/` and `backend/` at the repo root. Two (`parser/`, `gc-bot/`) are real, load-bearing production services (see Section 4's Architecture for how they're wired into the Docker Compose stack); the rest are either a separate end-user tool, an explicitly non-production research effort, or one-off dev scripts that should not be mistaken for maintained tooling.

### `parser/` -- Replay parser service (Java, vendored fork of `odota/parser`)
A Java HTTP service built on `skadistats/clarity` (the same Java library OpenDota's own parser uses) that ingests a raw Dota 2 replay and emits structured JSON -- per-second player intervals, combat log, draft timings, wards, chat, item purchases, etc. This is a vendored copy of the open-source `odota/parser`, patched with one addition: real per-second HP/Mana, read directly off the hero entity (`Parse.java`/`Entry.java`) via the same `getEntityProperty()` mechanism the existing `life_state` field already used -- upstream's interval entries have no health/mana field at all. Everything else is unmodified upstream source, meant to be re-synced by diffing against a fresh `git clone` of `odota/parser`.
- `pom.xml`: Maven project (`com.opendota:stats`), depends on `com.skadistats:clarity:4.0.1`; shaded/uber-jar build, main class `opendota.Main` -- **not** Spring Boot, despite what earlier drafts of this doc assumed.
- `src/main/java/opendota/Main.java`: HTTP server on port 5600, 3 routes -- `/` (raw parse, streams `Parse`'s output), `/healthz`, and `/blob?replay_url=...` (downloads + auto-detects bzip2/zstd + parses + returns one aggregated JSON blob -- the mode the backend actually calls). Caps concurrent `/blob` requests via a bounded thread pool since each holds full in-memory copies of the raw + decompressed + parsed replay.
- `src/main/java/opendota/Parse.java`: The core parser -- Clarity callback handlers emitting `Entry` objects for intervals, combat log, draft/ban timings, pauses, wards, chat, cosmetics, Dota Plus XP, neutral item drops.
- `processors/*.mjs`: Node/ESM post-processing scripts mirroring OpenDota's own JS pipeline (metadata -> expand -> parsed-data -> teamfights -> all-players -> draft timings -> pauses). **Not used by the Java service itself** -- kept for reference/potential future use. `processMultiKillStreaks.mjs` is explicitly commented out/deprecated even within this reference set.
- Built via `parser/Dockerfile` (`maven:3.9.12-eclipse-temurin-21-noble`, `mvn clean install` at build time), published as `ghcr.io/hu1k1e/immortalplus-parser` by CI.

### `gc-bot/` -- Steam Game Coordinator resolver (Node.js)
A small single-file Express service (`index.js`) that stays logged into a dedicated Steam account (Dota 2 in its library) via a persistent Game Coordinator session, resolving the `cluster`/`replay_salt` pair needed to build a replay download URL for an arbitrary match ID. Exists because OpenDota/Stratz only reliably have replay metadata for matches someone's already looked up (empirically: OpenDota resolved ~1/40 random matches, Stratz 0/10 -- see `research/README.md`); a live GC session resolves any valid match ID directly from Valve, the same technique OpenDota's own "Retriever" service uses. Validated live: 25/25 previously-unresolvable matches succeeded through it.
- Uses `dota2-gc` (built on the actively-maintained `steam-user`), not the deprecated `dota2` npm package. Persists a Steam refresh token to disk after first login so restarts skip re-authenticating.
- Full HTTP API (3 routes, confirmed by reading `index.js` in full): `GET /health` (`{steamReady, gcReady, lastError}`), `POST /steamguard` (submits a pending Steam Guard code -- `{"code":"XXXXX"}`), `GET /resolve/:matchId` (`{match_id, cluster, replay_salt}`, or 503/404/502 depending on GC state).
- Documented, accepted risk: its dependency chain pulls in a `protobufjs` version with unresolved CVEs, mitigated by only ever decoding protobuf messages Steam's own GC sends back, never exposed outside the internal Docker network.
- Built via `gc-bot/Dockerfile` (`node:20-slim`), published as `ghcr.io/hu1k1e/immortalplus-gc-bot`.

### `draft-scanner/` -- Local screen-capture draft reader (Python, packaged as a Windows .exe)
A local companion app meant to run **on the user's own gaming PC** (not in Docker -- it needs real screen access) that watches the live Dota 2 client during a draft and reports picks/bans by reading the screen, not the game or any API. Exists because Ranked All Pick (and every mode except Captain's Mode) never exposes opponent picks/bans through any official channel -- not GSI, and per the 7.35d patch notes, not even Overwolf's sanctioned integration API.
- **Anti-ban-safety-relevant**: confirmed by reading the source that this tool does *only* screen-pixel capture -- `window_capture.py` uses `mss` + `win32gui` purely to locate the Dota 2 window (`FindWindow`/`GetWindowRect`), never opening a handle into the game process or reading its memory. Same safety category as OBS or Discord's screen share, not the category Valve has warned about banning for -- this subproject upholds the project's own "never read game memory" rule.
- Pipeline: polls the backend's `GET /api/draft/state` (GSI-fed) every 2s to detect an active draft, then every 1s captures the window, identifies picked heroes via ORB feature matching against cached reference portraits (`matcher.py`, `hero_icons.py` -- chosen over naive template matching after ground-truth testing showed the latter failing badly on Dota's in-game crop/zoom), reads the ban log via Tesseract OCR + fuzzy name matching (`ban_ocr.py`, since All Pick's auto-bans render as scrolling chat text, not an icon strip), and posts accumulated state to `POST /api/draft/screen-report`.
- `calibrate.py`: a dev-only tool (not shipped) for re-deriving the percentage-based screen regions in `regions.py` if the Dota client's layout ever changes.
- Packaged via `pyinstaller build.spec` into a standalone ~137MB Windows .exe (bundles the Python runtime, OpenCV, and a trimmed Tesseract install). No Dockerfile, not in CI -- end users just download and run it, pointed at the production backend by default (`IMMORTALPLUS_BACKEND_URL` env var to override).

### `research/` -- Recommendation-engine planning subproject (Python + Markdown, not deployed)
A separate, explicitly non-production planning/prototyping effort for a "hyper-personalized recommendation engine" (a "Stockfish for Dota" pitch, per `README.md`), deliberately kept out of the production Docker build/CI. Scope-corrected from a full self-play search engine (ruled out as needing datacenter-scale compute) down to two tractable pieces modeled on what chess engines get value from: a static win-probability evaluation function, and an "opening book" of precomputed per-hero/role/rank/patch benchmarks -- combined into "Expected Win Contribution" (EWC) scoring that annotates a real match's decisions against the book/model, chess-engine-eval-graph style.
- `README.md`: the technical-decisions doc -- live-validated API constraints (OpenDota's `/heroStats` gives free rank-bucketed hero win rates in one call; Explorer SQL returns fast but rejects `GROUP BY`, so aggregation happens locally), the three-tier data architecture (draft/outcome/rank needs zero replay parsing; lane/item-timing needs full parsing via this repo's own `parser/`; replays are never kept, only derived features), and the precomputed schema (`optimal_benchmarks`, `item_build_winrates`, `hero_matchup_matrix`, `draft_evaluation`).
- `build_plan.md`: the full 4-phase build plan plus ten explicitly named known limitations (smurfs skewing the winner sample, the hero x role x rank grid being huge and sparse, side win-rate bias, etc.) and their mitigations.
- `coaching_categories.md`: a comprehensive, editable list of "what does a player doing something wrong actually look like" -- categories A-J (Laning, Farming, Item/build choices, Teamfight decisions, Deaths, Vision, Objectives, Support-specific, Carry-specific, Whole-game impact), each flagged by priority and by whether the underlying data is already available, meant to be handed to a future building agent.
- `harvest_public_matches.py`: a resumable CLI harvester -- pages OpenDota's Explorer SQL endpoint for real matches in a given rank bracket, stores them to a local SQLite DB (`research/data/public_matches.db`), reuses the backend's own rate-limited `OpenDotaClient` rather than a second uncoordinated limiter. Done and validated live; the aggregate tables, model training, and EWC scoring engine are all not started.
